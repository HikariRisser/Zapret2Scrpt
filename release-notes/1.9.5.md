# 1.9.5

## Исправлено: ложные «СБОЙ» для IPv6 в отчёте

После включения `ipv4_only` (1.9.3) проверка IPv6 в отчёте (`--action report`)
всё равно пыталась подключиться к реальным AAAA-адресам сайтов и выводила
`СБОЙ … Network is unreachable`. Это создавало впечатление, чтоサイトы не
работают, хотя браузер использует IPv4 и всё открывается.

Теперь отчёт пишет для IPv6: `не проверяется (DNS ipv4_only)`.

## Разобрано по приложенному отчёту (без изменений в коде)

- **`LUA: circular: conntrack is missing but required`** — 4 предупреждения
  на 7055 обработанных пакетов (0,06%). Для части пакетов (RST, пустой
  payload) nfqws2 не передаёт conntrack в Lua; это штатное поведение,
  стратегия пропускает такой пакет. Обход работает: в отчёте `desync
  profile: 7055`, YouTube/Discord/RuTracker открываются.
- **`rawsend: sendto (1440): Message too large`** — 50 раз на 258 fake-отправок.
  Ограничение ядра на размер генерируемого пакета в nfqws2 (бинарник),
  исправляется только в самом nfqws2, не в конфиге скрипта. Трафик при этом
  проходит.
- **`dns: lookup failed … empty result`** в логах туннеля — домены
  (`ggpht.com`, `ytimg.com`, `cdn-telegram.org` и др.), у которых нет A-записи
  даже у публичных DNS. Это известные CDN-имена, используемые только для
  внутренних запросов; ошибка не влияет на открытие сайтов.

## Не исправляется в этом скрипте

В отладочном логе nfqws2 видны пакеты с `ifin=zapret2tun`: часть
туннелированного трафика дополнительно проходит через DPI-десинхронизацию.
Правила перехвата создаются внешним init-скриптом zapret2 (nftables), а не
нашим конфигом. Если это вызывает конкретные сбои (например,
`RECORD_LAYER_FAILURE` для fbcdn.net), нужно править init-скрипт zapret2.
